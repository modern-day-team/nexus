# Nexus v0.8~v0.11 开发计划

## Context

项目已发布 v0.2.0~v0.7.0（ReAct 内核、委派与流式透传、Redis/SQLite Session、OTel trace、fallback 熔断、结构化输出，CI 全绿）。用户确认下一阶段四个方向全做：HITL 审批回调、可观测性完善、会话管理器、健壮性与运维。沿用既定工作流：每版独立 git worktree（`../nexus-wt-<topic>`，分支 `feat/<topic>`）+ 子 agent 实现 + 我定契约并审查合并 + `go test -count=1 -race` 全绿后打 tag 推送（502/408 等 45-60s 重试）。

## 版本安排（两波并行）

### Wave 1（并行）：v0.8.0 HITL 审批回调 + v0.10.0 会话管理器

**v0.8.0（feat/hitl-approval，agent 包）**——难点版，单独一批
- 现状：`ToolApprover` 是同步函数（`agent/observe.go` approvedTool），调用方可阻塞等 UI，但没有结构化协议、审批请求也不进事件流。
- 设计：保持同步 Approver 不变；新增**事件流审批桥**：
  - `agent/approval.go` 扩展：`ApprovalRequest{CallID, ToolName, Arguments string}`、`ApprovalDecision{Allow bool, Reason string}`。
  - `agent/events.go`：`EventType` 新增 `EventApprovalRequest`；`Event` 新增 `Request *ApprovalRequest` 与 `Respond func(ApprovalDecision)`（决定句柄，Respond 内部向桥 channel 发送并只生效一次）。
  - 新 API `agent.NewInteractiveApprover(timeout time.Duration) (*InteractiveApprover,)`：实现 `ToolApprover`——每次工具调用生成 Request、经 ctx emitter 发事件、阻塞在内部 channel 等待 Respond；超时按拒绝处理（Reason="审批超时"）。`Options.ToolApprover` 直接接入，零内核改动。
  - 无 emitter（Chat 路径）时退化为直接拒绝并附提示（文档说明：HITL 仅适用于 ChatStreamEvents）。
  - 委派透传：`delegate_stream.go` 已转发全部事件，审批请求自动到达父事件流，Respond 通道在子工具侧闭合——需子 agent 验证嵌套场景。
- 测试：事件流收到 Request→Respond(Allow) 放行；Deny 走拒绝文案路径；超时拒绝；并发多工具调用各自 Request 独立；嵌套委派透传；-race。

**v0.10.0（feat/session-store，sessions 包为主）**
- `agent` 包新增 `SessionStore` 接口（新文件 `agent/sessionstore.go`）：`Session(ctx, conversationID) (Session, error)`、`Delete(ctx, id) error`、`Close() error`。
- `agent/memstore.go`：内存实现（sync.Map + per-id Session）。
- `sessions` 包适配：`NewRedisStore(client, ttl)`、`NewSQLiteStore(db)`（复用现有 RedisSession/SQLiteSession，key 按租户/会话 id 组合实现隔离）。
- TTL：Redis 原生；SQLite 加 `last_active` 列 + `NewSQLiteStore` 可选后台清理 goroutine（interval 参数，Close 停止）。
- 便捷 API：`agent.NewWithStore(ctx, store, conversationID, Options)`——从 store 取 Session 注入 Options.Session。
- 测试：多会话隔离、删除、Redis TTL 过期（miniredis 时钟）、SQLite 清理、并发取同一 id 得同一实例（内存实现）。

### Wave 2（并行）：v0.9.0 可观测性完善 + v0.11.0 健壮性

**v0.9.0（feat/trace-nesting，agent + otelx）**
- span 父子嵌套：`Options` 新增 `ContextCustomizer func(ctx context.Context, ev TraceEvent) context.Context`——内核在 `agent.go:126/159`（`withTrace` 后）与 `events.go:119`（`withEmitter` 外层）调用其返回的 ctx 作为整轮执行 ctx（传给 inner 与工具）。otelx 的 TurnStart hook 借此把 span 注入 ctx，tool span 变成 run span 的子 span。
- 属性补齐：`TraceEvent` 增加 `Model string`（Options 加 `ModelName string`，三条路径填入）；otelx 输出 `gen_ai.request.model`、`gen_ai.usage.cached_tokens`。
- 委派链：TraceTurnStart 事件在委派透传下自动覆盖（子 Agent 自身 hook 独立），文档说明 span 树形态。
- 回归：otelx 现有 3 个测试适配新 ctx 流转；新增父子嵌套断言（SpanRecorder 检查 ParentSpanID）。

**v0.11.0（feat/robustness，agent 包）**
- 工具超时与 panic 恢复：`Options.ToolTimeout time.Duration`——`observe.go` 的包装器内 `context.WithTimeout`（超时返回错误结果给模型而非崩轮次）+ `recover()`（panic 转 error 文本 "tool panic: ..."，不杀进程）。
- 事件流可配：`Options.EventBuffer int`（默认 64）；丢弃计数——eventSink 丢弃时 atomic 计数，`Agent.DroppedEvents() int` 导出（慢消费者可观测）。
- 会话快照：`agent.ExportSession(ctx, sess) ([]byte, error)` / `agent.ImportSession(ctx, sess, data)`——Messages 的 JSONL 序列化往返（复用 FileSession 的编解码约定），供调试回放与迁移。
- 测试：超时打断慢工具、panic 工具不崩且模型收到错误、EventBuffer 生效与丢弃计数、导出→导入→History 一致（含 ToolCalls）。

## 执行顺序与验证

1. Wave 1 两个子 agent 并行 → 我审查 → 各自 merge → `make ci` + `gh run list` 确认绿 → tag v0.8.0 / v0.10.0 推送。
2. Wave 2 同样并行处理 → tag v0.9.0 / v0.11.0。
3. 收尾：CHANGELOG.md 补四版、README 目录结构与内核增强章节更新、`sessions/otelx` 新 API 文档段。
4. 风险预案：v0.8 的嵌套委派审批若 eino ReAct 工具节点语义不允许阻塞（会卡父 turn），降级方案为"审批仅在顶层 Agent 生效、委派工具内直接拒绝"并在文档说明；两 Wave 都改 `Options`（追加字段在末尾），合并冲突小，用逐字段合并解决。
